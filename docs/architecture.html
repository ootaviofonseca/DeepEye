DeepEye

Um agente de dados self-driving — você descreve o objetivo em linguagem natural, o sistema planeja e executa um workflow, e entrega os artefatos prontos.

Em vez de uma resposta direta de chatbot, o DeepEye produz um DAG auditável que é compilado, validado, otimizado e executado por um engine inspirado em bancos de dados.

Desafios que o DeepEye resolve

Três limitações fundamentais dos sistemas "ChatBI" atuais:

C1
Heterogeneity Gap
Decisões reais exigem cruzar banco de dados SQL, arquivos CSV e PDFs juntos. Sistemas atuais são silos: Text-to-SQL só faz bancos; RAG só faz documentos.
✦ Resposta: Unified Multimodal Orchestration — protocolo de nó unificado que conecta todas as fontes
C2
Context Explosion
Em single-agent, toda a história, todas as ferramentas e todas as observações intermediárias ficam na mesma janela de contexto — causando alucinação.
✦ Resposta: Hierarchical Reasoning — cada AgentNode tem contexto privado isolado do planejador global
C3
Unreliability & Inefficiency
Execução sequencial, "black-box", difícil de debugar ou otimizar. Oportunidades de paralelismo ignoradas.
✦ Resposta: Workflow Engine — valida antes de rodar, paraleliza via topological sort

Protocolo Unificado de Nó

Todo componente do DeepEye — desde leitura de dados até geração de vídeo — segue o mesmo protocolo formal. Isso permite que o Planner raciocine sobre qualquer capacidade de forma homogênea.

Definição formal (do paper SIGMOD '26):

Lógica de execução interna
Clique em um símbolo para ver detalhes de implementação.
ToolNode Operadores Determinísticos
Execução determinística: O = f_code(I, C). Idempotente. Sem contexto de raciocínio. Ex: datasource.read, sql.execute
AgentNode Reasoners Probabilísticos
Execução probabilística: O ~ P(· | I, C, W_local, T_internal). Contexto privado e isolado. Ex: dashboard.generate, video.generator

Memory-Augmented Planner

O Planner usa dual-memory para traduzir requisições em DAGs executáveis: memória de curto prazo para o turno atual e base de conhecimento de longo prazo para reuso de workflows históricos.

⚡ Working Memory (Short-term)
  • Histórico de diálogo multi-turno
  • Variáveis intermediárias do workflow
  • Feedback de erros do Engine (ex: SQL inválido)
  • Estado da sessão atual
🗃️ Knowledge Base (Long-term, vector store)
  • Schema Metadata — colunas e tipos das fontes
  • Domain Documentation — PDFs, TXTs indexados
  • SOP Experience — workflows verificados e salvos
  • Templates de expert criados manualmente na UI

Sandbox Docker

Todo código Python gerado pela IA roda em containers Docker isolados por sessão — nunca no processo principal do servidor. O RuntimeControl service (porta 8010) é o único que acessa o socket Docker, mantendo a API principal sem privilégios elevados.

1
SandboxManager cria o container
get_or_create_sandbox(session_id) — um container por sessão, com volume workspace montado para persistir arquivos entre os nós do workflow.
2
Código enviado via RuntimeControl
O Celery worker manda o código gerado para :8010/execute. O RuntimeControl usa a Docker API para rodar dentro do container de sandbox.
3
Resultado via arquivo no workspace
O código salva output em CSV/JSON no volume compartilhado. O nó seguinte do workflow lê esses arquivos — dados fluem entre nós via filesystem, não memória.
4
ActivityTracker e cleanup automático
Idle > SANDBOX_IDLE_TIMEOUT → container para. Idle > SANDBOX_DESTROY_TIMEOUT → container destruído. Ao fechar o app, todos são destruídos.
Dashboard e Video usam imagens Docker separadas (Dockerfile.dashboard, Dockerfile.video-preview) lançadas por task — não são o mesmo container de sandbox Python.

Fluxo Completo — End-to-End

Clique em "Avançar" para percorrer o caminho de uma mensagem completa do usuário até os artefatos aparecerem na tela.

Passo 0 de 10
1
Usuário digita no chat
"@Sales Database @Financial Metrics — Analise as vendas globais de 2025, gere vídeo, dashboard e relatório."
2
Frontend → POST /api/v1/chat
Envia session_id, message e datasource_ids dos contextos selecionados.
3
Backend enfileira Celery task
Cria ChatTurn, enfileira run_agent_workflow() no Redis. Responde imediatamente com turn_id.
4
SupervisorAgent analisa a requisição
Recebe contexto dos datasources no system prompt. Decide: tarefa complexa → chama workflow_agent tool.
5
WorkflowAgent gera o DAG JSON
Plano com 6 nós: datasource.read + knowledge.search → sql.execute → video.generator + dashboard.generate + report.generate
6
Compiler → Validator → Optimizer
JSON compilado em objetos tipados. Validator checa schemas e DAG. Optimizer identifica datasource.read e knowledge.search como independentes → layer paralela.
7
Executor roda os nós em ordem topológica
Layer 1 (paralelo): datasource.read ∥ knowledge.search. Layer 2: sql.execute. Layer 3 (paralelo): video.generator ∥ dashboard.generate ∥ report.generate.
8
Nós com código rodam no Sandbox Docker
Python code, video rendering e dashboard generation executam em containers isolados. Arquivos de output salvos no volume workspace.
9
Artefatos persistidos no MinIO
Vídeo .mp4, dashboard JSON/URL e relatório HTML salvos no object storage com metadados no PostgreSQL.
10
Eventos SSE → Frontend renderiza
A cada nó concluído, AgentCallback publica no Redis → SSE chega ao frontend → painel direito exibe vídeo, dashboard e relatório em tempo real.

Como Estender

Adicionar um novo nó

# 1. packages/backend/app/node/<domain>/my_node.py
from deepeye.workflows.registry import NodeSpec
from deepeye.workflows.models import Port
from app.node.core.base import BaseNode

class MyExportNode(BaseNode):
    node_type = "data.export_csv"

    @classmethod
    def spec(cls) -> NodeSpec:
        return NodeSpec(
            type=cls.node_type,
            description="Export rows to a CSV file",
            inputs={"rows": Port(schema_="list[dict]", required=True, multiple=True)},
            outputs={"path": Port(schema_="string")},
            params_schema={"filename": {"type": "string", "required": True}},
        )

    @classmethod
    def build_handler(cls, db, user_id, sandbox=None):
        async def handler(node, inputs, context):
            rows = inputs.get("rows", [])
            filename = node.params.get("filename", "export.csv")
            # ... write to sandbox workspace ...
            return {"path": f"/workspace/{filename}"}
        return type("H", (), {"execute": staticmethod(handler)})()

# 2. Em packages/backend/app/node/__init__.py — adicione à NODE_MODULES:
# "app.node.<domain>.my_node"
# O registro é automático — /api/v1/workflow-nodes retorna o novo nó.
